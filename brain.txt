AI-Powered Criminal Network Analysis System
Project Structure & Approach Document
SIH 2026  |  Problem Statement ID: SIH26189  |  Ministry of Home Affairs — NCRB

1. Executive Summary
Criminal networks today operate across fragmented, heterogeneous data sources — FIRs, CDRs, financial transactions, surveillance reports, and intelligence feeds. Investigators manually stitching these together miss critical hidden connections and patterns. This project delivers an AI-powered investigation platform that automatically ingests messy crime data, resolves entity identities, constructs a knowledge graph, discovers hidden connections, detects suspicious patterns, and presents actionable intelligence through an investigator-facing visual dashboard.
Core Value Proposition:  From fragmented investigation records → connected intelligence graph → actionable investigative leads.

2. Problem Statement Analysis
The NCRB problem statement (SIH26189) identifies five core pain points that this system must directly address:
    • Data is fragmented across disconnected systems (FIRs, CDRs, financial records, surveillance).
    • Relationships between suspects are hidden and not immediately obvious from raw records.
    • Manual analysis is slow, labor-intensive, and prone to missing connections.
    • No unified intelligence picture exists across multiple evidence sources.
    • Investigators lack tools to quickly identify influential nodes in a criminal network.

The system is NOT just a graph visualizer — existing tools like IBM i2 Analyst's Notebook already do that. The real innovation must be in automatic discovery of hidden relationships from messy, unstructured, heterogeneous data. This distinction is critical for evaluation.

3. System Architecture Overview
The system is structured as a five-engine pipeline, where each engine produces output consumed by the next:
Engine 1 — Data Fusion Engine
Ingests and normalizes structured (CSV/JSON) and unstructured (PDF/text) data from FIRs, CDRs, financial records, surveillance reports, and intelligence feeds into a single internal schema.
Engine 2 — Entity Intelligence Engine
Extracts named entities (people, phones, vehicles, locations, organizations, bank accounts) from text using NLP, and resolves duplicates — determining whether 'Rahul Sharma', 'Rahul S.', and 'R. Sharma' are the same person.
Engine 3 — Network Intelligence Engine
Constructs a knowledge graph in Neo4j. Runs graph analytics: PageRank, Betweenness Centrality, Degree Centrality, Louvain Community Detection, and Shortest-Path queries to identify key actors and hidden sub-networks.
Engine 4 — Threat Intelligence Engine
Detects suspicious patterns using rule-based and ML anomaly detection: financial structuring, communication bursts, coordinated location activity, shared infrastructure, and network expansion over time.
Engine 5 — Investigator Copilot
An LLM-assisted query layer where investigators can ask natural-language questions. Every AI-generated statement is grounded in evidence from the graph — no hallucinations, full explainability.

4. Detailed Module Breakdown
4.1  Multi-Source Data Ingestion
The platform accepts the following evidence types via file upload or API endpoints:
    • FIR / Police Reports — PDF or plain text narrative documents
    • CDR (Call Detail Records) — CSV format: caller, receiver, timestamp, duration
    • Financial Transaction Records — CSV: sender, receiver, amount, timestamp
    • Surveillance Reports — JSON/text describing persons, vehicles, locations, times
    • Intelligence Reports — unstructured narrative text

All sources are parsed and normalized into a common internal schema using pandas, pdfplumber, and python-docx for structured and unstructured files respectively. A job queue handles asynchronous processing so the system remains responsive during large batch ingestions.
4.2  AI Entity Extraction
Entity extraction is implemented as a hybrid NLP pipeline combining:
    • spaCy pretrained NER — for PERSON, ORG, LOCATION, DATE entities from narrative text
    • HuggingFace Transformers (BERT-based NER) — for improved accuracy on domain text
    • Regex rule-based extractors — for rigid patterns: phone numbers (10-digit Indian), vehicle registration plates (e.g., KA01AB1234), bank account numbers, IFSC codes, UPI IDs
    • Domain gazetteer lists — for known Indian city/district names, common criminal organization types

Extracted entity types include: Person, Phone Number, Vehicle, Location, Organization, Bank Account, UPI ID, Transaction ID, and Event (meeting, call, sighting, crime).
4.3  Entity Resolution — Key Differentiator
Entity resolution is one of the most important and innovative components of this system. Investigators frequently encounter the same person recorded differently across sources (e.g., 'Rahul Sharma', 'Rahul S.', 'R. Sharma'). The system computes a composite Entity Match Score:
    • Name similarity (fuzzy string matching via RapidFuzz, phonetic matching via Jellyfish/Soundex)
    • Phone number match (exact and partial)
    • Location overlap (co-appearance at same coordinates or named locations)
    • Vehicle association match
    • Temporal overlap (activity in the same time windows)
    • Associate similarity (shared connections in the graph)

Entities scoring above a confidence threshold (e.g., 85%) are merged into a single canonical node in the graph. This directly addresses the core problem of fragmented, distributed data that the problem statement highlights.
4.4  Knowledge Graph Construction
All resolved entities and their relationships are stored in Neo4j as a property graph.

Node Types:
    • Person, PhoneNumber, Vehicle, Location, Organization, BankAccount, Event

Relationship Types:
    • CALLED, OWNS, VISITED, TRANSFERRED_MONEY_TO, ASSOCIATED_WITH, MENTIONED_IN, SPOTTED_AT, PARTICIPATED_IN

Every edge carries:
    • Evidence source (which document/record created this link)
    • Timestamp (when the relationship was observed)
    • Confidence score (based on extraction and resolution confidence)
    • Weight (call frequency, transaction amount, co-occurrence count)
4.5  Network Analytics
The Neo4j Graph Data Science (GDS) library is used to run the following algorithms on the constructed graph:
    • PageRank: Identifies globally influential individuals — those with high reach across the network.
    • Betweenness Centrality: Identifies brokers and intermediaries — people who sit between otherwise separate groups. High betweenness with low degree often indicates a hidden coordinator.
    • Degree Centrality: Identifies the most directly connected individuals (hubs).
    • Louvain Community Detection: Automatically discovers criminal clusters/cells — groups of entities that interact heavily with each other but less with the rest of the network.
    • Shortest Path (BFS): Finds the minimum-hop indirect relationship between any two entities — the backbone of the Hidden Connection Finder feature.
    • node2vec + Link Prediction: Generates graph embeddings and predicts likely hidden or undiscovered connections between entities — genuine AI-generated investigative insight.
4.6  Suspicious Pattern & Anomaly Detection
A dedicated anomaly engine uses a hybrid of rule-based detection and ML models (Isolation Forest, DBSCAN) to flag:
    • Financial Structuring — rapid sequential transfers just below reporting thresholds (e.g., ₹9,800 → ₹9,700 → ₹9,500 within hours), indicating deliberate layering.
    • Communication Bursts — sudden spike in call frequency between previously low-activity entities.
    • Coordinated Location Activity — multiple suspects appearing at the same location within a narrow time window.
    • Shared Infrastructure — multiple unrelated suspects sharing a phone number, device, vehicle, or bank account.
    • Network Expansion Events — sudden growth of an entity's connections in the graph within a short time period.
4.7  Temporal Intelligence
The system tracks how the criminal network evolves over time. Investigators can replay the network's growth from any start date to end date, observing:
    • When new entities entered the network
    • When new links formed between previously unconnected clusters
    • Periods of unusual activity (call spikes, transaction surges)

This 'Investigation Replay' feature is a compelling differentiator — most competing systems only show a static snapshot. Temporal analysis reveals the sequence of events that built the criminal network.

5. Signature Features
5.1  Hidden Connection Finder
An investigator selects any two entities that appear unrelated. The system finds the shortest indirect path connecting them through the graph, with full evidence at each hop. For example:
    • Person A  →  Phone X  →  Person B  →  Vehicle Y  →  Person C  →  Person D
Each arrow is backed by evidence (call record, vehicle sighting, transaction). This is a powerful demo moment: two suspects with no apparent direct connection are revealed to be just 4 hops apart through shared infrastructure.
5.2  Evidence-Backed Relationships
Every relationship in the graph displays its full evidence trail on click:
    • Source document (CDR_1023, FIR_204, SURV_044, TXN_882)
    • Nature of relationship (17 phone calls, ₹2,50,000 transfer, co-appearance at Location X)
    • Confidence score (e.g., 94%)
This prevents the system from being a 'black box' and makes it auditable — critical for a law enforcement use case.
5.3  Risk Scoring with Explainability
Every entity receives a composite Risk Score (0–100) based on:
    • Number and risk level of direct connections
    • Betweenness centrality (broker role)
    • Volume of financial activity
    • Frequency of flagged location appearances
    • Communication patterns with high-risk entities

Importantly, the system never labels anyone a 'criminal' — it flags entities as 'high-priority investigative persons of interest based on observed patterns and connections,' maintaining legal and ethical responsibility.
5.4  AI Investigator Copilot
Investigators can ask natural-language questions such as:
    • "Show me everyone connected to Rahul within 2 hops."
    • "Why is Amit considered high risk?"
    • "Find all entities that called phone 9876543210 in the last 30 days."

The LLM generates responses grounded exclusively in evidence from the graph — not from general knowledge — eliminating hallucination risk. Every statement links back to a source record.

6. Investigator Dashboard — 5 Investigation Views
View 1 — Network Graph View
Interactive graph built with Cytoscape.js. Investigators can zoom, filter by entity type, click nodes to see profiles, and expand connections. High-risk nodes and detected communities are color-coded.
View 2 — Timeline View
Horizontal timeline of all events (calls, transactions, meetings, sightings) across the case. A slider allows investigators to scrub through time and watch the network evolve (Investigation Replay).
View 3 — Entity Profile View
Detailed panel for any selected entity: risk score, all connections, associated evidence documents, timeline of activity, known locations, vehicles, and phone numbers.
View 4 — Alerts Panel
Live feed of anomaly detections ranked by severity and confidence. Each alert links directly to the evidence that triggered it and the entities involved.
View 5 — AI Investigation Assistant
Natural-language query interface backed by the knowledge graph. Answers are evidence-grounded and auditable.

9. Synthetic Demo Dataset — Operation Shadow Link
Since real case-level criminal network data is not publicly available (and should not be used without authorization), a realistic synthetic investigation dataset is generated using Python (Faker + custom scripts). This is standard practice in academic and research contexts for this problem domain.

Dataset structure:
    • 3 FIR narrative text files (deliberately fragmented information)
    • 2 surveillance reports (JSON)
    • 5,000 CDR call records (CSV)
    • 2,000 financial transaction records (CSV)
    • 150 vehicle sighting records (CSV)
    • 200 intelligence report snippets (text)

Hidden ground truth planted in the dataset:
    • A kingpin connected to 4 core associates and 8 peripheral entities
    • A financial structuring chain (10 transactions just under ₹10,000 threshold)
    • Two clusters connected only through a single broker entity
    • Shared phone infrastructure across 4 apparently unrelated suspects

The demo presents the raw noisy data to judges, runs the pipeline live, and the system automatically discovers the planted ground truth — verifiable by judges in real time.

10. Scope Boundaries — What NOT to Build
To maintain focus and deliver a deep, polished prototype rather than a shallow wide platform, the following are explicitly out of scope:
    • Facial recognition or biometric identification
    • Predictive crime forecasting (predicting who will commit a future crime)
    • Real-time nationwide police surveillance
    • Scraping real social media profiles of real individuals
    • 50+ different ML models — breadth over depth does not win
    • A generic dashboard with fake data — every number in the demo must be real pipeline output

11. Security, Privacy & Data Governance
For a Ministry of Home Affairs / NCRB use case, judges will explicitly evaluate data governance. The following must be implemented and presented:
    • Role-Based Access Control (RBAC) — investigators, supervisors, and admins have different data access levels
    • JWT-based authentication — all API endpoints are secured
    • Encryption at rest — pgcrypto for PostgreSQL sensitive fields
    • TLS/HTTPS — all data in transit is encrypted
    • Immutable audit trail — every investigator query, data access, and system action is hash-chained and logged
    • No determination of guilt — the system generates investigative leads, not criminal verdicts
    • Architecture mentions integration pathways with CCTNS and ICJS (even if not implemented in the prototype) — demonstrates domain awareness

12. Unique Selling Proposition & Pitch
Do NOT pitch:
"We use AI and graph analytics to analyze criminal networks." — This is generic and describes existing tools.

Pitch instead:
"Our system transforms fragmented investigation records into an explainable intelligence graph — automatically extracting entities from unstructured text, resolving identities across data sources, discovering hidden multi-hop connections, detecting suspicious patterns, and showing investigators exactly what evidence supports each lead."

Evaluation hierarchy for judges:
    • Entity Intelligence — 'Who is actually who?' (entity resolution)
    • Evidence Fusion — 'What connects them?' (cross-source relationship discovery)
    • Network Intelligence — 'Who plays what role?' (centrality, community detection)
    • Pattern Detection — 'What is suspicious?' (anomaly engine)
    • Investigator Copilot — 'What should I look at next?' (explainable AI)
